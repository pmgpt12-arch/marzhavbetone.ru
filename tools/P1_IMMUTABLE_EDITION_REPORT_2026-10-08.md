# P1: фиксация издания при создании заказа

Дата: 2026-10-08. Кандидат исправления: отдельный worktree codex/p1-immutable-edition-20261008 от 065153a980bc244cc2e4c65fa213b7a045a4e931.

Статус: локальная техническая проверка пройдена. Не опубликовано. Не юридическая приёмка. Не SALE_READY.

## Проверенный дефект

Прежняя схема сохраняла sku/name/price и basename общего ZIP. Новая выдача пересобирала тот же путь по времени изменения текущих мастеров. Во временной проверке через настоящие функции OLD_EDITION старого заказа заменился на NEW_EDITION после подготовки нового заказа; SHA старого ZIP изменился.

Причина: общий изменяемый кэш одновременно служил историческим экземпляром заказа. Класс ошибки: потеря состава приобретённого издания при обновлении каталога/мастеров. Правило: издание фиксируется до заказа/платёжного API; повторная выдача читает исключительно закреплённый экземпляр. Контроль: регресс tools/test_p1_immutable_edition.php.

## Изменение

Для новых P1 payment.php сохраняет серверное edition={zip,sha256} до записи pending-заказа и обращения к API. Клиентское edition не принимается. SKU, цены, страницы, сервисы не изменены.

products-config.php собирает упорядоченный ZIP с фиксированными временами записей, имя p1-<sha256 самого ZIP>.zip. Временный файл публикуется атомарным rename под отдельной неблокирующей файловой блокировкой P1; занятая блокировка возвращает отказ 503 до создания заказа. Исходники читаются дважды, изменение состава во время сборки отменяет снимок. Проверяется содержимое, а не mtime: изменение в ту же секунду и удаление файла учитываются. Повреждённый существующий снимок не перезаписывается сборкой.

mvb_prepare_delivery сохраняет уже выданные basename, токен, срок, счётчик и отметку письма. Новому P1 выдаётся его edition; метаданные дублируются в delivery.editions.p1. Ошибка любой позиции по-прежнему отменяет выдачу всего заказа.

download.php проверяет имя и SHA закреплённого снимка до увеличения счётчика. При отсутствии/повреждении отвечает 500; счётчик не расходуется, восстановления по актуальным мастерам нет. Имя скачиваемого файла остаётся обычным каталожным именем. Для legacy P1 отсутствующий ZIP тоже не пересобирается из текущих мастеров.

Legacy P1 с уже выданным delivery.items сохраняет существующий ZIP без приписывания исторического хеша. Legacy P1 без выдачи и без edition блокируется с причиной «издание P1 не зафиксировано; требуется миграция». Реальные заказы не читались и не изменялись.

## Обязательный gate перед публикацией

Это отчёт/план, не выполненная миграция. Публикация изменённых мастеров P1 запрещена до следующих проверок:

1. Read-only инвентаризация фактических P1-заказов: pending/waiting_for_capture/paid, наличие items.edition и delivery.editions, basename, срок, счётчик. Не выводить контакты, токены, ключи.
2. Для всех старых заказов без pin установить авторитетный исходный архив соответствующего издания. Доступный сейчас общий ZIP не доказывает состав на дату покупки: его могли уже перезаписать.
3. Dry-run таблица order-id → подтверждённое издание/SHA, список BLOCKED и резервная копия исходных заказов/архивов. Не собирать исторический комплект из новых мастеров.
4. Если исходный архив отсутствует/не подтверждён: BLOCKED. Владелец подтверждает конкретный восстановленный состав и SHA для перечисленных заказов либо определяет ручную выдачу. Без этого подстановка актуального продукта запрещена.
5. Отдельной принятой операцией создать неизменяемые снимки из подтверждённых архивов и под существующей блокировкой заказа записать edition в items и delivery, сохранив id, цену/название, статус, токен, срок, downloads, email_sent_at. Legacy ZIP сохранить для отката; токены не менять.
6. Проверить побайтовое совпадение повторного скачивания до/после миграции и отрицательные missing/corrupt сценарии. Убедиться, что отсутствуют необработанные legacy pending-заказы: иначе последующая оплата будет корректно заблокирована.
7. Только затем публиковать изменения P1. orders/delivery и связанные снимки сохранять; очистка не должна удалять архивы закреплённых заказов.

## Ограничения

Реальный сервер продаж, действующие заказы, платёжный провайдер и доставка писем не проверялись. Это локальные технические тесты контура. Предметная/юридическая полнота продукта, оформление, согласованная цена и публикация остаются отдельными критериями приёмки.

Остальные SKU используют прежний mtime-кэш; исправление намеренно ограничено P1. Повторная выдача ранее issued-позиций сохраняет их basename. Для P1 snapshot lock конфликт даёт контролируемый 503, ожидание блокировки не происходит.
