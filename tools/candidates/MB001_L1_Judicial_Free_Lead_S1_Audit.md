### 3.1 Пробелы, которые реально мешают KPI

- **P1. Лид не знает статью.** `lead.php:131–136` уже принимает `content_id`, но форма его не шлёт. Связать лид со статьёй можно только косвенно: `session_id` у `content_viewed(статья)` → `content_viewed(dengi)` → `magnet_delivered`, если всё в одной вкладке. **[Ф] дополнительно:** `lead.php` чистит `content_id` регэкспом `[^a-zA-Z0-9_\-.]`, поэтому путь `/articles/x.html` превратится в `articlesx.html`. Передавать надо slug, а не путь.
- **P2. Клик во врезке не виден в F**, а в M не различается по статьям.
- **P3. `sku` S1 не распознаётся** браузерным извлечением (`attribution.js:360`).
- **P4. Оплата не связана с лидом серверно.** Это зона GF-1 #252 (`payment.php` меняется только по отдельной команде владельца, #250/#251). **Не дублировать.** До GF-1 KPI S1 считать по Метрике: `purchase` с `product_id` содержащим `s1` + сегмент «достиг `checklist_download`».
- **P5. Внутренние UTM перезаписывают last touch.** `attribution.js:467–479`: переход по ссылке `?utm_source=site&utm_medium=post-delivery` делает `last = {source:"site"}`. Для отчёта «какой канал принёс деньги» last touch у покупок из цепочки будет «site». First touch сохраняется. **[В]** Это приемлемо, если канал считать по first touch, а внутренние метки по `utm_content`. Трогать сейчас не нужно, но это надо знать при чтении отчёта.

### L1-A. Атрибуция «статья → лид → S1» в существующем потоке (измеримость)

**Зависимость:** не зависит от S1, кроме пункта 3. Можно делать раньше, если владелец разрешит правку аналитического кода.
**Файлы:** только `attribution.js` + тест `tools/test_browser_events.js`.

**Приёмка:** в тесте браузерных событий есть случаи: клик по врезке → `cta_clicked` с парой; submit формы → в FormData есть `content_id` в виде slug без `/`; страница `/products/s1-….html` → `sku:"s1"`. `check_goals.py` без расхождений (новых целей Метрики нет). `event.php`, `lead.php`, `payment.php` не изменены.
