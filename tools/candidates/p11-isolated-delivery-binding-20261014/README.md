## Привязка

Builder проверяет точные исходные Git blob и уникальность каждого якоря, создаёт только временные копии существующих `mvb_prepare_delivery`, `mvb_deliver_and_notify`, `mvb_delivery_email` и `download.php`. Корневые runtime-файлы не изменены. `binding_helpers.php.txt` — текст фрагмента, не самостоятельный исполняемый PHP-модуль.

Новый консолидированный P11 выбирается только по явному sandbox-флагу `MVB_P11_CANDIDATE_BINDING=true` и точному серверному признаку издания `p11-t6-gold-20261014` с SHA/именами ZIP и письма. В этой задаче признак назначает только тест; реальный checkout/payment его не назначает. Sandbox задаёт каталог двух принятых источников: `accepted.zip` и `accepted-letter.txt`. Производственный путь не назначен.

Архив не пересобирается: принятые ZIP/TXT копируются в неизменяемые имена в тестовом DELIVERY_DIR, под неблокирующей блокировкой. Повторная выдача использует выданный снимок, не текущие мастера. Письмо дословно включается в существующее уведомление со сформированной ссылкой; новым router/queue/dispatcher это не является.

Прежние P11/T6 сохраняют архив, токен, сроки и счётчик. **Не только повтор старого заказа, но и новый незамаркированный заказ P11/T6 не пересобирает общий исторический ZIP.** Он получает существующий исторический архив либо отказ при его отсутствии. Это исключает перезапись файла, на который ссылаются старые покупки. Утраченные исторические публикации восстанавливаются отдельной проверенной процедурой; их восстановление здесь не заявляется.

2. `cross-order-failure.json` и `cross-order-probe.py`: на историческом `f0efb917…` новый unmarked P11 вызвал общий изменяемый сборщик и перезаписал архив прежних покупателей.
