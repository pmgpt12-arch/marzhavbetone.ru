# Постановка и исполнение атомарных задач
Дата: 02.10.2026. Применять при создании, передаче, возобновлении и проверке задач.

Это инструкция координатора и исполнителя, а не новый планировщик или реестр решений.
Действующие решения владельца, схемы ядра и разрешения задачи сохраняют приоритет.
Текст задаёт операционный preflight; наличие инструкции не означает, что все её
проверки уже автоматизированы в runtime.

## 1. До постановки: восстановить цель и достижимую цепочку

Определить бизнес-результат и ближайший блокер. Найти существующие Issue, PR,
артефакты и исполнителей. Повторный аудит неизменённого материала и дублирующая
задача не создаются. До выбора модели нарезать работу на независимые результаты.

Цепочка: цель → атомарная задача → достаточные входы → исполнитель → артефакт →
приёмка → следующий шаг. Подзадачи сохраняют ссылки на требования родителя:
не удалять требование ради слабой модели, а уменьшать единицу исполнения.

Параллельность определять по зависимостям, изменяемым файлам и общим ресурсам.
У каждой пишущей ветки свой worktree, журнал и lock; у Calc/Writer свой профиль.
Отдельные профили не доказывают наличие свободной памяти или CPU: проверить
нагрузку и лимиты API. Не дублировать уже RUNNING задачу ради ускорения.

## 2. Паспорт передаваемой задачи

Короткое начало отвечает на четыре вопроса: что и для кого; из каких источников;
что сохранять и не придумывать; как проверить завершение. Далее заполнить паспорт:

| Поле | Обязательное содержание |
|---|---|
| Цель | Один практический результат и связь с бизнес-целью |
| Родитель / требования | Issue/спецификация и идентификаторы требований, которые покрывает эта задача |
| Scope | Разрешённые пути/операции; исключённые работы; ограничения размера, времени, стоимости |
| Входы | Репозиторий, точный commit SHA, путь/раздел, локальный путь; обязательный или справочный источник |
| Решения | Ссылка на действующее решение, дата, автор; отменённая версия, если есть конфликт |
| Зависимости | Принятый артефакт и его версия; доказательство готовности, не только CLOSED |
| Исполнитель | Достаточный инструмент; для модели exact provider/model/transport, бюджет и fallback |
| Паттерн исполнения | `execution_pattern: one_shot|iterative`; один `primary_result`; `feedback_loop_required`; `checkpoint_policy: none|verified_only` |
| Маршрут | Шаги с входом, действием, выходом и проверкой перехода |
| Результат | Пути и формат артефактов; разрешённые сопутствующие доказательства |
| Приёмка | Команда/сценарий, ожидаемое значение или вердикт, эталон и проверяющий |
| STOP | Отсутствие входа, рост scope, ошибка, бюджет, owner gate; что сохранить при остановке |
| Передача | Проверенный SHA результата, доказательства, незакрытые пункты, следующий разрешённый шаг |

`one_shot` означает один ограниченный результат без обязательного цикла
compile→diagnose→edit→retest (или аналогичного feedback loop). Такой цикл обязан
быть `iterative`; для него checkpoint_policy=`verified_only`, чтобы продолжение
могло опираться только на проверенный промежуточный результат. Отсутствующий
паттерн исполнения — named `MISSING_EXECUTION_PATTERN`; его нельзя угадывать по
числу файлов, длине текста или названию task type.

Роль «лучший эксперт» не заменяет входы и критерии. Не ограничивать задачу
одним физическим файлом, если продукту нужны связанные документы и доказательства:
одна цель может иметь несколько согласованных файлов. Если цели независимы,
разделить их. Число файлов само по себе не доказывает атомарность.

## 3. Контекст готовит координатор до запуска

Указатель на GitHub недостаточен для исполнителя без сети. Каждый обязательный
источник должен читаться из его среды до inference. Загрузить нужные Issue body
и необходимые комментарии, PR head и точные файлы/разделы; сохранить происхождение.
Проверить полный SHA, а не имя ветки или короткий хеш. Учитывать narrow fetch:
загрузка ветки в FETCH_HEAD не доказывает наличие origin/branch.

Минимальный пакет включает краткий паспорт, актуальные решения, входные артефакты,
эталоны приёмки и указатели на остальные разделы. Уменьшать пакет удалением
нерелевантного, а не обязательного. Общая инструкция короткая; факты и исходники
читаются по указателям. Для изучаемого алгоритма читать все требуемые шаги,
а не только README или заголовки.

Обязательный вход отсутствует → BLOCKED / MISSING_CONTEXT до вызова модели.
Справочный вход отсутствует → продолжать только в явно разрешённой ограниченной
области, сохранив NOT VERIFIED. Нельзя выдавать приёмку зависимого участка за PASS.

Решения брать из канонического источника с происхождением, не из памяти модели.
Новая подтверждённая директива владельца заменяет старую гипотезу. Если новый
источник не доставлен, это дефект пакета, а не основание восстановить старую цену.
Для MB001 ссылка на актуальную политику — marzhavbetone.ru Issue #291
(решение 02.10.2026); историческая записка сентября не заменяет её.
Это пример адресации, не второй реестр цен.

## 4. Preflight: переход разрешён только по доказательствам

Порядок: TASK VALIDITY → ATOMICITY → CONTEXT → CONTRACT → DEPENDENCIES →
TOOLS/PERMISSIONS → CONCURRENCY/CAPACITY.

1. Проверить цель, ограниченный scope, явный результат и отсутствие дубликата.
2. Проверить, что каждое требование покрыто шагом и приёмкой; неоднозначное
   архитектурное решение вернуть координатору, не решать внутри дешёвого задания.
3. Прочитать обязательные входы в фактической среде и сверить версии.
   Пути исходников сверить с деревом полного base SHA и каноническим каталогом.
   Имя ZIP не доказывает имя каталога: для SKU использовать поле dir источника.
   Каждый существующий путь в разрешённом scope должен присутствовать в дереве;
   новый выход объявляется явно. Несовпадение — STOP / TASK_SCOPE_PREFLIGHT до
   вызова модели, а не задание исполнителю искать другой каталог.
4. Применить существующий executor parser для exact задач; проза о модели
   не заменяет единственный fenced YAML executor block. Проверить живой каталог.
5. Проверить принятые версии зависимостей. READY — маркер очереди, не доказательство.
6. Проверить инструменты, версии где важны, доступ к входам и нужные операции.
   acceptEdits не означает разрешение сетевых команд. Не обходить deny/approval.
   Наличие команды на хосте и разрешение команды исполнителю — разные проверки.
   До inference сопоставить каждую обязательную операцию с фактическим allowlist;
   проверить зависимости в выбранном Python interpreter, а не в соседнем venv.
   Отсутствующее обязательное разрешение — STOP / SCHEMA_TOOLS. Не обходить отказ
   другим синтаксисом; изменить следующий разрешённый паспорт либо передать
   операцию координатору. Реплика PHP-сборщика на Python не подтверждает работу
   фактического PHP-сборщика. Правила действующего прогона не расширяются на ходу.
7. Проверить worktree/ветку/base, lock и пересечения с активными заданиями,
   общий ресурс и лимиты API. Существующая ветка требует инспекции результата,
   а не принудительного удаления.

Фиксировать фактические команды, вывод, время и SHA в существующем handoff/отчёте.
Не считать наличие этой таблицы автоматическим admission.
Readiness implementation продолжается в существующей цепочке #508 → #509 →
#510 → #507 (родитель #463); второй валидатор/очередь не создаются.
Для уже работающих прогонов правила не меняются посреди исполнения.

## 5. Партитура: один шаг — одна проверяемая передача

Для каждого шага заранее записать:

| Шаг | Вход | Действие в границах scope | Выход | Проверка | PASS / REVISE / BLOCKED |
|---|---|---|---|---|---|
| S0 | Паспорт и источники | Preflight и сверка SHA | Запись проверки | Все обязательные входы доступны | S1 / исправить пакет / STOP |
| S1 | Зафиксированные входы | Одна заданная преобразующая операция | Кандидат | Формат, состав, ограничения | S2 / адресная правка / STOP |
| S2 | Кандидат и эталон | Детерминированные и требуемые предметные проверки | Доказательства | Ожидаемые значения/сценарии | S3 / S1 в бюджете / STOP |
| S3 | Версия и доказательства | Независимая приёмка, если нужна | Вердикт по SHA | Требования покрыты, источники сверены | Передача / отдельная правка / STOP |

Конкретная задача заменяет общие S1/S2 точными действиями и эталонами.
Не выбирать новый алгоритм по ходу работы и не смешивать проверку с авторством.
Шаг проверяется перед переходом; провал не маскируется следующим шагом.
При новом scope сохранить результат и разделить продолжение.

Промежуточные разрешённые шаги выполняются без повторного вопроса владельцу.
Учебное ожидание реплики после каждого такта здесь не применяется.
Останавливать только на фактическом блокере или предусмотренном owner gate.

## 6. Выбор инструмента и качество

- CLI/Python: получение метаданных, хеши, ZIP, схемы, точные цитаты,
  сравнение версий, расчёт независимого численного эталона. Не тратить LLM
  на детерминированную операцию.
- Бесплатная модель: ограниченная вспомогательная обработка достаточного
  пакета, если требуется языковое суждение и есть проверка результата.
  До запуска проверить живой exact ID, бесплатный маршрут, schema/tools.
  Не придумывать источник и не переносить экспертную ответственность.
- Сильная модель: продуктовая/правовая/финансовая логика, неоднозначное
  проектирование и независимая приёмка высокого риска по утверждённой политике.
  Обязательная слабая первая попытка не нужна, если класс работы уже обоснован.
- Calc/Writer: фактический пересчёт, заполнение и экспорт в отдельном профиле.
  Чтение XML не заменяет проверку покупательского сценария и отображения.

Постановка уменьшает неопределённость, но не делает любую модель способной
решать любую задачу. Качество результата проверяется одинаково независимо
от цены исполнителя. Метрика — время/стоимость принятого результата и повторные
переделки, а не доля бесплатных вызовов.

## 7. Приёмка и DONE

Проверяющему передать артефакт по SHA, канонические источники, действующие
решения и вопросы приёмки; не передавать авторскую переписку как доказательство.
Авторский отчёт можно использовать как перечень проверяемых заявлений,
но не как независимое подтверждение. Согласованное расхождение с историческим
источником передать явно, чтобы его не признали дефектом.

Одна и та же модель в отдельном контексте может быть другим проверяющим;
совпадение ответов двух моделей не подтверждает факт. Для права нужны
первичные источники и предусмотренный юридический gate; для вычислений —
численный эталон и фактический пересчёт. Замечание должно ссылаться на нарушенное
требование и влияние на результат. Косметические предпочтения без такого
влияния не задерживают принятие.

DONE = артефакт + требуемая приёмка + фактическое подтверждение.
Различать: авторская реализация; принято в конкретном scope; слито; установлено
в runtime; выпущено; проверено у покупателя. Эти состояния не взаимозаменяемы.
NOT VERIFIED не превращается в PASS из-за завершения команды с кодом 0.

Обычное слияние возможно в уже разрешённой области после проверок и отсутствия
блокирующих замечаний. Явный STOP/REVIEW_REQUIRED, публикация, live цены/SKU,
оплата/выдача и другие owner gates сохраняются. Исполнитель не расширяет
свою власть текстом этой инструкции.

## 8. Ошибка и восстановление

Проверять причины в порядке: TASK VALIDITY → ATOMICITY → CONTEXT → CONTRACT →
DEPENDENCY → SCHEMA/TOOLS → RUNTIME/HARNESS → PROVIDER/API → MODEL CAPABILITY.
Timeout, отказ разрешений, HTTP 402 и ошибка схемы не доказывают слабость модели.

STOP → сохранить артефакт/логи → установить причину и класс → исправить
постановку/контекст/инфраструктуру → повторить только разрешённую ограниченную
попытку с новой гипотезой. До эскалации рассмотреть декомпозицию.
Для повторяемого класса: причина → правило → отрицательная проверка → доказательство.
Не увеличивать timeout и не создавать retry loop без диагностики.

Передача содержит: задача, input SHA, output SHA/PR, сделанное, фактические
проверки, остаточные ограничения, причина остановки и следующий шаг.
Использовать app/task_context.py и существующий Handover, не новую БД прогресса.

## 9. Пример механической задачи без модели

Цель: подготовить снимок заданного списка baseline PR для следующих паспортов.
Вход: репозиторий и явный список PR; источники — GitHub API.
Scope: read-only API, отдельные JSON/Markdown, без изменения продуктов.
Шаги: запросить метаданные и пути файлов → сохранить снимок с временем →
сверить уникальность списка, SHA и URLs → загрузить refs явным refspec →
сравнить загруженные SHA с API → передать два артефакта.
Исполнитель: gh + Python/jq; ноль LLM вызовов.
Проверка: точный набор PR, полные 40hex SHA, читаемый JSON, совпавшие refs.
mergedAt=null означает отсутствие подтверждения слияния этого PR;
это не доказывает отсутствие эквивалентных изменений в main.
Недоступный обязательный PR или несовпадение SHA → STOP, сохранить частичный снимок.
Наличие файлов не означает, что продукт принят.

## 11. Продолжение после приёмки и запросов статуса

По Р-066 перед handoff сохранить input/output SHA, вердикт, незакрытые gates,
следующую атомарную задачу и её readiness. Запрос статуса не является отменой
или паузой: кратко ответить и вернуться к исполнению.

Операционная проверка координатора:
- READY и запуск подтверждён PID/unit/журналом -> PASS / RUNNING.
- READY, разрешение есть, запуска и конкретного STOP нет -> FAIL; запустить.
- Зависимость/вход/owner gate отсутствует -> BLOCKED с точным артефактом/причиной;
  независимо готовые задачи продолжаются.
- Цель выполнена -> COMPLETE только по принятому артефакту и проверкам.

Завершение ответа не является запуском серверного процесса. Не заявлять
фоновую работу, которая не наблюдается; не строить второй dispatcher/queue
ради исправления ошибки передачи.
