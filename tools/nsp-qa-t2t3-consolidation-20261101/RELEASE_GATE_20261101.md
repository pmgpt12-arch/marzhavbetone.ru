## 3. Транзакционный gate публикации

Текущий публикационный executor P4 v1 (`tools/nsp-publication-20261026/p4-v1-20261030/operate.py` и `current-only/publish.php`) жёстко привязан к SHA старого 26-файлового архива, счётчику 26 и staging-имени `P4-v1-current.zip`. Он **не может быть повторно использован для 30-файловой редакции простой сменой request.json**. Не вызывать старую команду `p4-publish` с новым SHA. Для P5 аналогично требуется адаптация и проверка точной версии.

Точный release должен: сделать read-only snapshot текущих P4/P5 и страниц; проверить передний SHA, статус живых платных SKU, отложенную публикацию и отсутствие активных задач; подготовить изолированный staging с двойным архивным SHA/member gate; выполнить адресную публикацию только разрешённых P4/P5 файлов и их карточек; проверить фактический скачиваемый ZIP байт-в-байт против одобренной редакции; выполнить rollback при дофинальном FAIL. Не изменять чужие SKU, кассу, действующий поток заказов.

Только после положительной приёмки новых P4/P5 снять T2/T3 как самостоятельные предложения: каталог, диагностика, CTA в статьях, цены и metadata. Не удалять исторические заказы, уже выданные токены и старую выдачу; новые заказы T2/T3 должны отвергаться на серверной стороне, даже при прямом POST.

## 5. Контроль ошибки и правила

Повторяемые причины: `TASK/CONTRACT` (нельзя выдавать QA-отчёт за permission), `VERSION_DRIFT` (жёсткие SHA старого publisher), `TOOL_SAFETY_BLOCK` (отказ до запуска), `NATIVE_OFFICE_BUSY` (старый WINWORD может оставаться), `HISTORICAL_ORDER_REGRESSION` (снятие SKU не равно удалению заказа). 

Каждый случай: наблюдаемый отказ → первопричина → класс → точечное правило → автоматический gate → проверяемая квитанция. Никакого blind retry, массового merge/deploy PR #677 или переноса QA на ноутбук.
