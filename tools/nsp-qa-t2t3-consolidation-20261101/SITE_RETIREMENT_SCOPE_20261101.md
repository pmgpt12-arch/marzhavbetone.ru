- Сведения старых заказов, legacy SKU и возможность использовать ещё действующие ссылки не удаляются ради снятия карточек. Нельзя направлять новых покупателей к SKU, уже исключённому из продаж.

## Почему нельзя просто удалить SKU из products-config.php

В действующей схеме `mvb_prepare_delivery()` использует `mvb_resolve_product()` при обработке оплаченного заказа, а `download.php` при отсутствии готового ZIP может вызвать `mvb_build_product_zip($sku)`. Удаление старого определения товара или его исходной папки способно сломать старую оплаченную выдачу. Выбор — **оставить legacy resolution, запрещать только новые заказы**. Старую выдачу проверять отдельно; срок ссылки и лимит скачиваний остаются прежними (3600 секунд/30 скачиваний по конфигурации).

## Проверки перед и после адресного релиза

1. Положительные: P4/P5 карточки ведут к правильной новой редакции, цена неизменна, актуальный ZIP байт-в-байт совпадает с одобренными SHA.
2. Отрицательные: прямой POST с T2/T3 и смешанная корзина с T2/T3 отвергаются до создания заказа/обращения к платёжному провайдеру.
3. Исторические: старый оплаченный заказ T2/T3, действующий токен, заданная версия/кэш и правила TTL успешно обслуживаются; старые заказы и customer data не изменяются.
4. Контент: отсутствуют самостоятельные цены 9 900/14 900 в действующей витрине/CTA; в JSON-LD и sitemap не остаются устаревшие товарные предложения; редиректы и canonical не создают циклов.
5. Остальные SKU: P1/P2/P3/P7/P8/P9/P10/P11/P13 и их маршруты оплаты/выдачи не изменились; сравнение с before snapshot.
6. Фиксация DONE: Git SHA patch, per-file before/after SHA, native receipts, тесты, HTTP доказательства, rollback receipt, подтверждённый production outcome. Не объявлять продажу обновлённой, если нет проверки на боевом сервере.

## Важный обнаруженный дефект письма покупателю

В точном `products-config.php` staging/publication P4 v1 map `acceptedStarts` указывал на несуществующий `00-START-HERE.txt`, хотя архив P4 имеет одну PDF-инструкцию `00-INSTRUKCIYA.pdf`. P5 не имел явного точного имени инструкции, использовалась общая эвристика. На ветке PR #681 исправлено **только** это сопоставление для P4/P5; код проверен повторным чтением GitHub, **не опубликован**.

## Самокоррекция покрытия от 02.11.2026

Исходный перечень из 18 точек оказался **неполным**: поиск по публичному дереву исходного сайта обнаружил ещё два бесплатных материала — `materialy/akt-skrytyh-rabot.html` и `materialy/uderzhaniya.html` — с самостоятельными карточками T2/T3. Они теперь исправлены в QA-ветке. **Класс ошибки:** `PUBLIC_NAVIGATION_INVENTORY_INCOMPLETE`; первопричина — аудит выборки URL без контрольного поиска по всем публичным HTML/PHP/JS. **Новое правило/gate:** перед релизом выполнить полный поиск старых SKU/URL и цен во всём текущем production snapshot и проверять отсутствие новых ссылок на T2/T3, включая бесплатные материалы; сохранённые исторические QA-снимки и заказы исключать из требования удаления. Предварительный поиск на исходном репозитории выполнен, но он не заменяет финальный production snapshot.

Состояние QA-ветки: все 20 адресных точек подготовлены; старые товарные URL содержат страницы с разъяснением переноса, `noindex,follow` и canonical на P4/P5. Настоящий HTTP 301 ещё **не настроен** — метод и место его установки необходимо определить после проверки конфигурации боевого хостинга. Цены на P4/P5 не меняются. 6 изменённых Word прошли нативную проверку и визуальный контроль всех 16 страниц, Excel №44 пока не прошёл нативный gate. Не выдавать подготовленные страницы за live и не снимать оплату только из-за существования этой записи.
