# NSP — gate реального платежа и окончательного переключения

Статус: **HOLD / подготовка**, 20.10.2026. Не является разрешением включить боевые платежи, почту или 301. Проверенная стадия: GitHub Actions [39423577670](https://github.com/pmgpt12-arch/marzhavbetone.ru/actions/runs/39423577670).

## Подтверждённое состояние

- Новый домен обслуживает тестовый noindex-сайт; `payment.php`, `webhook.php`, `check-payment.php`, `contact.php` для POST возвращают HTTP 503.
- 18/18 страниц и все 13 ZIP по HTTPS проверены; 172/172 файлов совпадают по SHA-256; 13/13 просроченных ссылок дают HTTP 410. Переход `/get/?k=gu` — 302 на действующий Telegram-бот, неизвестный ключ — 404.
- На старом сайте действуют live-ключи ЮKassa; SITE_URL — старый домен; ссылки действуют 3600 секунд. Текущие секреты и заказы не копировать в репозиторий.
- На новом сайте пока отсутствует боевой `config.php`. Старый магазин и его обработчики продолжают работать.
- Тестовая позиция `test1` уже есть в серверном каталоге: 100 копеек, скрытая страница `/test-pokupka.html`. Это не четырнадцатый продаваемый SKU; 13 коммерческих SKU остаются без изменений.
- Последний полный манифест и четыре проверенных резервных архива сохранены в приватной директории хостинга, SHA — в evidence. Рабочие заказы не восстанавливать из старого снимка при откате.

## Порядок следующих атомарных операций

1. **Read-only provider audit.** Подтвердить текущие адреса webhook ЮKassa и возможность обратимого переключения. Не менять webhook и не выводить ключи в логи. Проверить действующий SMTP/From, SPF/DKIM или оставить старого проверенного отправителя.
2. **Live-config preflight.** Сформировать на хостинге *только в приватной временной директории* новый `config.php` из текущего действующего: SITE_URL — новый HTTPS-домен; абсолютные ORDERS_DIR, DELIVERY_DIR и PRODUCTS_DIR — те же, что сейчас; секреты без изменения. Сравнить исходный и новый конфиги после разрешённой адресной замены без вывода содержимого. Проверить права 0600 и недоступность HTTP. Проверить, что тестовый обработчик не создаст параллельный каталог заказов.
3. **Controlled 1 ₽ checkout gate.** В согласованное окно кратковременно активировать только тестовую покупку `test1` на новом домене с защитой от остальных покупок до проверки. Владелец проходит реальную оплату 1 ₽. Сохранить ID/статус без платёжных секретов. Синтетические заказы не засчитывать.
4. **Provider webhook + email + ZIP.** Подтвердить получение подписанного/проверенного уведомления, одну обработку заказа, однократную отправку письма, HTTPS-ссылку нового домена, фактическое скачивание и отказ HTTP 410 после срока. Повторный webhook не должен создавать повторное письмо/архив. Платёжные POST не переводить обычным 301.
5. **Buyer acceptance.** После теста включить все 13 SKU, сверить цены из `products-config.php`, ZIP состав и 172 SHA-256; подтвердить недоступность мастеров, конфигурации, заказов и кэшей. Сравнить фактические заказы/количество файлов до и после, не раскрывая персональные данные.
6. **SEO и перенаправления.** Только после buyer gate: включить обычные 301 со старого домена на новый с сохранением пути/query; отдельные правила для payment/webhook/check-payment/download и старых оплаченных ссылок. Проверить apex/www, HTTPS, отсутствие циклов, canonical, sitemap, robots, аналитику, кабинет поиска и контроль SSL-продления.
7. **Permanent GitHub Actions.** Перенастроить целевые пути `DEPLOY_PATH` и конфигурацию публикации после сравнения с реальным хостингом; deploy не должен перезаписывать config.php, заказы, кэши и 172 покупательских файла. Завершить отдельным verified report с коммитом и Actions run.

## Откат

- При ошибке тестовой покупки, webhook или письма: **STOP** новые оплаты, восстановить прежний webhook и прежнюю конфигурацию обработки. Не удалять/не перезаписывать актуальные заказы. Возврат к старому действующему сайту должен быть проверен до снятия ограничений.
- Откат тестового нового webroot — через существующую транзакцию `publish_test.py --rollback-only` **только если** текущий tree SHA и ожидаемый статус совпадают; не запускать слепо, когда появились новые реальные заказы.
- 301 включать последним; при дефекте сначала отключить 301, проверить старые POST и скачивание уже выданных ссылок.
- Полный rollback и его фактическая проверка — отдельные evidence, не предполагать по завершению команды.

## Gate на запуск

Нельзя считать реальную оплату принятой без действий владельца с платежом 1 ₽ либо другого реально подтверждённого платёжного сценария. До этого статус остаётся **STAGING PASS / PAYMENT HOLD**, даже при 13/13 синтетических скачиваниях.

Сохранить классификацию четырёх старых замечаний общего CI; не выдавать весь CI за зелёный. Новые ошибки миграции классифицировать отдельно и устранять на минимальном уровне.
