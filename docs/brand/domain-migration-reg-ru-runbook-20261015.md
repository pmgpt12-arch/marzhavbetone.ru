# Регламент R2 — подключение nastoronepodryadchika.ru и безопасный перенос
**Дата:** 2026-10-15 · **Источник:** [Issue #653](https://github.com/pmgpt12-arch/marzhavbetone.ru/issues/653) · **Статус:** подготовлено; переключение НЕ выполнено.

## 0. Установленные факты, а не предположения
- Пользователь подтвердил покупку `nastoronepodryadchika.ru`.
- Проверено из ai-workstation через WHOIS ТЦИ: `REGISTERED, DELEGATED, UNVERIFIED`, `REGRU-RU`, `created 2026-10-15T10:26:33Z`, `paid-till 2027-10-15T10:26:33Z`; NS в WHOIS: `ns1.hosting.reg.ru`, `ns2.hosting.reg.ru`.
- Проверка из ai-workstation: новый корневой домен и `www` не разрешались DNS и не отвечали по HTTPS (проверка 2026-10-15).
- Старый `marzhavbetone.ru` и `www` разрешались на адреса Cloudflare и отвечали HTTPS 200 (www — после перехода на без-www); NS `ruben.ns.cloudflare.com`, `love.ns.cloudflare.com`. Эти IP **НЕ являются подтверждённым origin**.
- Старый MX: `mx1.hosting.reg.ru`, `mx2.hosting.reg.ru`; не ломать почту.
- В репозитории `.github/workflows/deploy.yml` предполагает виртуальный хостинг Рег.ру: `SITE_PATH=secrets.DEPLOY_PATH || www/marzhavbetone.ru`, `PRODUCTS_PATH=secrets.DEPLOY_PRODUCTS_PATH || products-marzhavbetone`. Реальные значения секретов и продакшен-каталог **не подтверждены**.
- В `config.php` коммита значения ЮKassa представлены placeholders; они НЕ доказывают рабочую конфигурацию production.
- Деплой использует `rsync/lftp --delete` с исключениями `orders`, `config.php`, `products-storage`, `.well-known`. **Не** менять путь `DEPLOY_PATH`, пока не выполнен отдельный preflight на новый каталог.
- Новый визуальный стиль утвержден для *подготовки макетов*; финальный выбор/код/публикация проверяются отдельно.

## 1. Архитектурное решение
**Не менять хостинг сейчас.** Новый сайт готовится на том же тарифе/аккаунте Рег.ру, что и старый, но в **отдельном каталоге**. Для итогового домена предпочтителен Cloudflare (как у старого), однако начать следует с корректной привязки нового домена к Рег.ру и выяснения фактического origin IPv4; затем добавить отдельную Cloudflare-зону. Не копировать Cloudflare A/AAAA старого домена как IP хостинга. Не переносить и не удалять старые заказы.

## 2. Действия владельца в Рег.ру (без передачи паролей)
**2.1 Проверка контактов регистратора.**
1. Открыть https://www.reg.ru/ → войти в свою учётную запись → **Домены** → `nastoronepodryadchika.ru`.
2. Проверить, что домен в списке, срок до 15.10.2027, NS `ns1.hosting.reg.ru` и `ns2.hosting.reg.ru`.
3. Посмотреть, есть ли требование подтвердить контактные данные/адрес почты: в WHOIS `UNVERIFIED`. Если регистратор требует подтверждение — выполнить его в кабинете. Не путать состояние регистрационных данных с DNS.
4. Пока **не** менять NS на Cloudflare, не включать переадресацию на старый сайт.
**Контроль:** снимок экрана с названием домена и состоянием NS (скрыть личные данные).

**2.2 Определить рабочую услугу хостинга.**
1. Рег.ру → **Мои услуги / Хостинг** → открыть именно ту услугу, на которой размещён `marzhavbetone.ru`.
2. Записать (без секретов) тип панели (ispmanager / cPanel / Plesk), **IP сервера (origin IPv4)**, название тарифа, количество доступных сайтов, путь корня действующего сайта.
3. Не использовать IP Cloudflare (`104.21.14.97`, `172.67.158.155`) как origin.
**Контроль:** панель показывает старый сайт и origin IPv4; тариф разрешает второй сайт.

**2.3 Привязать новый домен к этому хостингу без изменения старого.**
- Для ispmanager: раздел **Сайты → Создать сайт**, домен `nastoronepodryadchika.ru`; alias `www.nastoronepodryadchika.ru` (если предусмотрен).
- Создать **отдельный** document root, например `www/nastoronepodryadchika.ru` только если панель предлагает такой путь; ничего не переносить из `www/marzhavbetone.ru` вручную и не запускать старый `setup-server.sh`.
- Включить корректную поддержку PHP той же версии, что на работающем сайте, и HTTPS; не публиковать пока второй дублирующий коммерческий сайт.
- При NS `ns1.hosting.reg.ru/ns2.hosting.reg.ru` DNS обычно создаётся в панели хостинга (Рег.ру прямо указывает это в официальной инструкции). Проверить `@` и `www` (A/CNAME) в панели **Управление DNS**, не создавать записи в кабинете регистратора в неподходящем разделе.
**Контроль:** новый домен и www разрешаются на **origin IPv4**, новый vhost отвечает на тестовую страницу, старый сайт без изменений.

**2.4 Выпустить SSL на origin.**
- В ispmanager → **Сайты** → новый сайт → **SSL / Let's Encrypt**. Сертификат должен покрывать основной домен и `www`.
- Если выдача не проходит — проверить DNS и существование vhost; не включать Cloudflare Flexible как обход.
**Контроль:** HTTPS нового сайта работает без предупреждений (TLS ≥1.2).

## 3. Подключить новый домен к Cloudflare (после определения origin)
1. Авторизоваться в том Cloudflare-аккаунте, где уже подключён `marzhavbetone.ru`.
2. **Add a site** → `nastoronepodryadchika.ru`; выбрать подходящий план (бесплатного достаточно для стартового сценария). **Не** добавлять домен как поддомен старого.
3. В DNS новой зоны задать `A @ → <подтверждённый IPv4 origin из панели хостинга>`; `CNAME www → nastoronepodryadchika.ru` (или равнозначное решение). На A/CNAME включить proxy **только после** успешного origin SSL и проверки ответов. Не копировать IP Cloudflare другого домена.
4. Не добавлять MX/SPF/DKIM/DMARC без принятого решения об отдельной почте; пока действующий контактный `marzhavbetone@yandex.ru` сохраняется.
5. Cloudflare покажет **собственную новую пару NS** для этой зоны; перейти в Рег.ру → новый домен → **DNS-серверы и управление зоной** → заменить `ns1.hosting.reg.ru/ns2.hosting.reg.ru` **только на пару, показанную для нового домена в Cloudflare**. Нельзя автоматически использовать `ruben/love` старой зоны.
6. Подождать активации зоны и проверить authoritative NS; в Cloudflare → **SSL/TLS → Full (strict)** после origin cert; включить **Always Use HTTPS** после smoke. HSTS preload пока НЕ включать.
7. Оценить WAF, Cache Rules, Page/Redirect Rules старой зоны и перенести лишь безопасные настройки — не копировать платежные исключения не глядя.
**Контроль:** `http://` → HTTPS; `https://www.` → без-www; сертификат валиден, `/index.html`, `/styles.css`, `/katalog.html` доступны на новом хосте; нет циклов переадресации.

## 5. Платежи и права старых покупателей — обязательный gate
1. Снимок текущей working payment chain: создание заказа → уведомление ЮKassa → успешная оплата → письмо → download token.
2. Для новой редакции подтвердить route успеха и ошибки, доступность нового webhook URL `https://nastoronepodryadchika.ru/webhook.php`, корректную обработку `payment.succeeded`.
3. В ЮKassa для Basic Auth: **Интеграция → HTTP-уведомления**. URL изменять **после** доступности нового хоста и тестовой оплаты, не заранее. Не создавать параллельные уведомления без проверки идемпотентности.
4. Протестировать реальные данные по одному разрешённому тестовому платежу с заказом и выдачей; сверить лог заказа, письмо, ссылку на скачивание и его срок действия. Не подменять тестовым `config.php` рабочий сервер.
5. **Старый покупательский токен должен работать после миграции.** Варианты — общий безопасный `ORDERS_DIR` для старого/нового или временное сохранение старого download endpoint без редиректа; выбрать по фактическому состоянию.
6. Почтовые `From`, SPF/DKIM/DMARC и доставку отдельно; не менять существующий working support e-mail по одной лишь причине ребрендинга.
**Контроль:** 1 тестовая покупка + проверка одного старого действительного права скачивания + публично недоступные master файлы; FAIL по любому пункту = no release.
